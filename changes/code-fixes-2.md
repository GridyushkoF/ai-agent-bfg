## БД

Исправить следующие проблемы:

Нет пагинации у списка чатов. ChatRepository.search выбирает все чаты пользователя
и сортирует их по updated_at desc, id desc. Индекс ix_chat_user_updated (user_id, updated_at) 
для этого подходит, но при большом числе чатов в ответ уходит весь набор.

Нет пагинации у истории сообщений. 
MessageRepository.findByChat забирает все сообщения чата вместе с полным content.
Одно сообщение может быть до 16 000 символов, так что длинный чат превращается в 
тяжёлый GET /api/v1/chats/{chatId}. Для модели история уже обрезана: findLatest берёт последние 40 сообщений. 
Клиентский ответ не обрезан.

Поиск по заголовку не использует индекс по тексту. 
Условие lower(title) LIKE '%запрос%' с процентом в начале не ложится на обычный B-tree. 
Сейчас Postgres отбирает чаты пользователя по ix_chat_user_updated и фильтрует заголовки уже в этом наборе. 
Пока чатов у человека немного, это дёшево. Когда их станут тысячи, каждый такой поиск будет просматривать все его строки. 
Для подстроки нужен trigram-индекс, например pg_trgm по lower(title).

Индексы не совпадают с сортировкой. ix_chat_user_id полностью перекрывается индексом (user_id, updated_at), а ix_message_chat_id уже индексом (chat_id, created_at).
Оба лишних индекса только замедляют вставку. Для пагинации из файла индексы лучше сразу сделать для ORDER BY: (user_id, updated_at DESC, id DESC) и (chat_id, created_at DESC, id DESC). 
Сейчас id в индексе нет, и при одинаковом времени Postgres досортирует строки отдельно.

Время в ответах приходит в разных поясах
При создании чата время собирается в Java как UTC и в JSON выглядит как Z. 
При чтении timestamptz драйвер отдаёт его в поясе JVM, и тот же момент приходит как +03:00

Поток SSE упирается в маленький пул chatStreamExecutor содержит 8 потоков и очередь 200, 
а каждый ответ блокирует поток до 4 минут на blockLast. Сообщение пользователя уже сохранено в SaveUserMessageService.prepare, 
и только потом задача попадает в пул. Если очередь заполнена, 
RejectedExecutionException уходит клиенту как 500, а сообщение в чате остаётся.

Неудачный ответ модели тоже оставляет сообщение пользователя 
Заголовок при следующей попытке строится уже по новому тексту, 
а в историю модели попадают два пользовательских сообщения подряд без ответа между ними.

Код конфликта логина и почты определяется по тексту исключения.
RegisterUserService ищет в сообщении Postgres подстроку ux_app_user_email. 
Если формулировка другая, занятая почта вернётся как LOGIN_TAKEN. 
Отдельного теста на EMAIL_TAKEN нет.

title-max может разъехаться со схемой. В yaml лимит 120,
колонка chat.title тоже varchar(120). Если поднять только настройку, setTitleIfAbsent
упадёт по ограничению колонки,
ошибка проглотится, и чат останется без заголовка.
