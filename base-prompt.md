# Промпт для ИИ-чат бота
Агент с ИИ: пользователь отправляет задание на сервер, сервер обращается к внешнему AI-сервису
(open ai compatible)
получает ответ и отправляет прогресс/результат пользователю асинхронно (SSE)

## Стек
Java 25, Spring boot 4+, PostgreSQL, jOOQ, liquibase, spring ai, security, docker/compose

## Архитектура

1. Архитектура: feature-based вместо mvc-based. Каждая фича в своей папке и содержит все что ей нужно(контроллеры мапперы репозитории и тд)
2. Lombok обязателен. Records не трогаем.
    - DTO: `@Builder @Data @AllArgsConstructor @NoArgsConstructor`
    - Сервисы и прочие бины: `@RequiredArgsConstructor` + `final` поля. `@Autowired` на поля не ставим.
    - Hibernate-сущностей нет. База через jOOQ.

3. Общая папка `platform`.
   Там:
    - `@ControllerAdvice` + иерархия исключений (базовое `AppException`, бизнес, валидация, техническое).
    - Глубокая логика spring security
    - Общие конфиги (`@Configuration`).
    - Общие утилиты, константы, базовые интерфейсы.

4. Нейминг.
    - DTO сетевые: постфикс `Request` / `Response`. Слово Dto не пишем.
    - Вложенные структуры: статические классы внутри Request/Response, тоже с ломбоком. Отдельные файлы не создаём.
    - Внутренние объекты (не торчат наружу): постфикс `InternalState`.
    - Сервис: `...Service`
    - Контроллер: `...Controller`
    - Репозиторий: `...Repository`
    - Пакеты в единственном числе (`user`, не `users`).

5. Пакетная структура.
   ```
   com.company.project
   ├── platform
   │   ├── exception
   │   ├── security
   │   ├── config
   │   └── util
   ├── feature
   │   ├── user
   │   │   ├── controller
   │   │   ├── service
   │   │   ├── repository
   │   │   ├── dto
   │   │   └── mapper (если есть)
   │   └── order
   │       └── ...
   └── Application.java
   ```
   jOOQ-сгенеренный код кладём отдельно (обычно `com.company.project.jooq` или в target, но в исходниках не мешаем).

6. Репозитории.
   Работают только с `DSLContext`. Никаких Spring Data JPA.
   Методы репозитория возвращают либо jOOQ-типы, либо сразу InternalState. Не торчат наружу сырые Record'ы если можно избежать.

7. Валидация.
   На всех Request'ах `@Validated` + Spring Validation аннотации.
   Кастомные валидаторы если надо, живут рядом с фичей или в platform.

8. Обработка ошибок.
   Все бизнес-ошибки кидаем своими исключениями из platform.
   `@ControllerAdvice` ловит всё, мапит в единый формат ответа (код + сообщение + детали).
   Стек трейсы наружу не отдаём.

9. Маппинг.
   Если сложный, используем ручной отдельный маппер класс постфикс ManualMapper.
   если простой - mapstruct интерфейс постфикс AutoMapper
   Мапперы живут в фиче.
   В сервисах маппинга быть не должно

10. Конфигурация и профили.
    `application.yml`
    Секреты через env или vault, не в репе.
    jOOQ, datasource, security конфиги в platform.config...

11. Миграции.
    liquibase, формат чистый SQL
    jOOQ генерится после миграций.

12. Тесты.
    Структура зеркалит основную.
    Юнит-тесты на сервисы (мокаем репозитории).
    Интеграционные на контроллеры + репозитории (Testcontainers).
    Не пишем тесты ради тестов.
    Важно чтобы корректно работал тестовый кэш (единый тестовый DI-контейнер со всеми зависимостями)

13. API.
    Префикс `/api/v1`.
    Версионирование через path.
    OpenAPI (springdoc) подключаем, чтоб сваггер был из коробки.

14. Логирование.
    SLF4J + Logback. В сервисах логируем вход/выход на debug, ошибки на error.
    Не логируем чувствительные данные (пароли, токены, персоналку).

15. Классы
    Длина класса не более чем 100 строк, при превышении делать паттерн Фасад.
    то есть будет субпакет, в нем фасад и отдельный сервис на каждый метод фасада
16. БД
ID - UUID
Индексы всегда на внешние ключи и потенциально нагруженные аттрибуты
17. Развертка
Применяем локальную базу данных и профиль local
Используем docker-compose для генерации необходимого окружения

## Требования
### Пользователи
Слой пользователь отвечает за регистрацию и авторизацию пользователей
должна быть возможность создать аккаунт и войти в него, авторизация JWT
Без сложной авторизации, у пользователя просто логин пароль и почта, при этом никаких кодов на почту отправлять не нужно
это доп.поле может пригодится позже
### Чаты
Каждый пользователь имеет список чатов, может искать по ним и переключаться
Каждый чат хранит историю переписки с чат-ботом
Чаты должны иметь осмысленное название, которое будет 1 раз сгенерировано AI при первом запросе пользователя
### Логика переписки с ботом
Пользователь получает ответ в формате md в реальном времени через SSE-генерацию
